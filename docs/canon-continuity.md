# 正史连续性与长篇记忆

本文描述系统当前的正史事实链、人工复核门和长篇上下文注入规则。这里的“正史”指作者确认、能够追溯到当前权威正文的故事事实，不等同于规划稿、模型猜测或旧缓存。

## 为什么需要独立正史层

长篇失控通常不是单纯的上下文窗口不足，而是以下对象被混成了一份状态：

- 规划中打算发生的事；
- 正文里已经发生的事；
- 模型从正文中抽出的候选事实；
- 作者确认后的权威事实；
- 已被新版正文取代的旧事实。

如果抽取结果直接进入人物状态、时间线或下一场提示词，一次错抽就会在后续章节中自我强化。当前实现因此把“抽取”“逐条裁决”和“确认清单完整”分开：模型只能产生候选，逐条接受只记录审核结论；所有候选处理完后，还必须通读当前终稿并明确确认没有漏项，系统才会在一个事务内把整场事实切换为运行时正史。

## 权威状态模型

| 对象 | 状态 | 能否进入后续生成上下文 |
| --- | --- | --- |
| 规划事件 | `planned` | 只作为计划约束，不冒充已发生事实 |
| 正文抽取候选 | `pending` | 否 |
| 作者逐条接受、场景尚未核验 | 候选为 `accepted`，事件仍为 `pending` | 否 |
| 场景核验后的已接受事实 | `accepted` | 是 |
| 作者拒绝的候选 | `rejected` | 否 |
| 被新版终稿取代的事实 | `superseded` | 否 |

一次接受会产生不可变的单条审核 `CanonCommit`，但事件仍留在运行时之外。只有场景完整核验成功，系统才在同一事务中停用上一版正史、激活本版已接受事件、更新计划时间线兑现关系，并重建场景与章节级 `ContinuitySnapshot`。运行时人物、关系、物品、知识和时间线投影只读取完成这一边界后的 `accepted` 事件；待确认、仅逐条接受、已拒绝、纯规划和已失效事件都不会进入下一场提示词。

事件回放还会独立复核：正史事件必须同时拥有有效的单条审核提交、有效的场景完成提交，并且两者都绑定当前实际正文哈希。单独篡改 `accepted`、`synced` 或快照状态不能绕过这一条件；旧式原地改文一旦造成哈希漂移，旧证明会被隔离并要求重新核验。提取器没有返回正文引文时，系统保留“无证据”状态，不会用任意正文片段代填。

场景正史完成还必须同时满足：

1. 指向当前 `FinalScene`，不能复用上一版终稿的结果；
2. 不存在待裁决候选；
3. 场景快照为 `complete`；
4. 快照引用至少一个有效的场景完成提交（`author_verification` 或 `facts_unchanged`），单条候选接受提交不能冒充全场完整；
5. 提交记录中的正文哈希与当前终稿完全一致。

旧的 `narrative_sync_status=synced` 本身不再构成证明。历史场景第一次进入新版流程时会显示待复核，需要作者完成一次提取/裁决或明确核验。

## 作者工作流

在高级模式打开 `成稿中心`，进入“正史”页签：

1. 对待提取或降级场景点击“用模型重新提取”。模型未配置时接口会明确返回 `409`，不会伪造离线结果。
2. 对每条候选核对正文证据。证据必须是当前终稿中的精确片段，否则即使点击接受也会被服务端拒绝。
3. 人物名称存在歧义时，先选择项目内的真实实体，再接受；无法可靠归一时保持待确认。
4. 接受真实事实，拒绝误抽或无关内容。
5. 无论模型返回若干候选还是空列表，都要在完整阅读当前终稿后填写说明并执行场景核验，确认候选清单没有遗漏持久事实。

只有章内所有场景都有当前终稿、且正史状态全部完成，章节才可批准、确认通读或导出。正文发生新修订后，旧版未完成候选立即失效；上一版已提交正史作为“最后一次已确认事实”保留到新版完成核验，在完成边界上再与旧时间线兑现引用一起原子失效。新版仍必须针对当前终稿重新处理，不能用旧提交证明当前正文。

人工提升正文时可以显式声明 `facts_unchanged`，但来源版本必须已有完整、正文哈希匹配且仍有效的正史提交。系统会为新终稿建立可追溯的延续提交，而不是偷偷复用旧正文哈希；不声明或来源尚未完成正史核验时，仍需重新提取、裁决并核验。

## 提取配置与失败语义

归档时的自动正文事件提取是可选能力：

```powershell
$env:NOVEL_SYSTEM_LLM_ENABLED = "true"
$env:NOVEL_SYSTEM_LLM_EVENT_EXTRACTION_ENABLED = "true"
```

未启用自动提取时，场景保持 `pending_extraction`，作者仍可从“正史”页签显式发起。供应商失败、解析失败或发送前拒绝会记为 `degraded`，不会把“没抽出来”解释成“没有事实”。模型返回空列表或若干候选都需要作者在逐条裁决后做场景级完整性确认，避免漏抽被静默放行。

## 长篇上下文注入

下一场的冻结 Bundle 只追加最近已提交的连续性变化，包括人物状态、知识、关系、物品、时间线和未偿叙事义务。POV 知识变化会按当前视角人物过滤，避免把其他人物掌握的秘密泄漏给写作者模型。

长篇硬锚点分为两类：

- 契约显式引用和仍为 `pinned` 的锚点始终注入；
- 已 `faded` 的硬锚点只有与当前章、场景、人物或查询文本相关时才召回。

召回结果会把策略、查询哈希和选择原因写入冻结 Bundle 的 provenance，便于复算。当前本地回退使用结构字段与 Unicode/CJK 词法相关性，不宣称它具有向量语义能力；真实向量后端仍需独立验证。

## API

主要接口如下，所有写操作均支持现有的可选持久化幂等键：

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| `GET` | `/api/v1/projects/{project_id}/canon/scenes/{scene_id}` | 读取场景候选、证据和快照 |
| `POST` | `/api/v1/projects/{project_id}/canon/scenes/{scene_id}/extract` | 显式运行正文事实提取 |
| `POST` | `/api/v1/projects/{project_id}/canon/scenes/{scene_id}/candidates` | 从当前终稿精确证据手工建候选 |
| `POST` | `/api/v1/projects/{project_id}/canon/candidates/{candidate_id}/decision` | 接受或拒绝候选 |
| `POST` | `/api/v1/projects/{project_id}/canon/scenes/{scene_id}/verify` | 确认本场候选清单完整、没有漏项 |

接口会校验项目归属、当前终稿 ID、证据片段、实体归属和候选终态。针对已被替换的终稿操作会返回冲突，不会修改当前正史。

## 数据迁移

本功能由 Alembic revision `20260818_0082` 提供（当前 head 为 `20260904_0083`）。升级真实数据库前先停止服务并按运行安全文档完成可验证备份，再执行：

```powershell
cd backend
.\.venv\Scripts\python.exe -m alembic current
.\.venv\Scripts\python.exe -m alembic upgrade head
```

迁移不会把历史正文自动伪造为已复核正史。升级后按成稿中心列出的待处理场景逐一核验。

## 已验证与仍需实测的边界

离线回归覆盖了候选隔离、证据校验、实体歧义、幂等裁决、正文换版失效、章节审批门、POV 过滤、锚点相关性和迁移结构。这证明工程契约可重复执行，但不能证明某个真实模型的事实抽取召回率，也不能替代真实 5 章/30 章写作耐久和作者盲评。发布前仍需使用真实供应商、真实作品与固定检查点完成独立验收。
